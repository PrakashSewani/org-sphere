# ADR-003: Event-Driven Architecture

## Status

Accepted

## Date

2025-01-15

## Context

OrgSphere consists of multiple modules (Employee, Leave, Attendance, Approvals, etc.) that need to communicate. Direct service-to-service calls create tight coupling and make the system harder to evolve.

## Decision

OrgSphere will use an event-driven architecture. Modules communicate through domain events published to an event bus. Consumers subscribe to events they need. This enables loose coupling and audit trail by default.

## Consequences

### Positive

- Loose coupling between modules
- Audit trail by default
- Temporal decoupling
- Event sourcing potential
- Easy to add new consumers

### Negative

- Eventual consistency (not immediate)
- Debugging more complex
- Event schema evolution needed
- Ordering guarantees required

### Neutral

- Need event bus infrastructure (Kafka, RabbitMQ, etc.)
- Need event schema registry
- Need to design event versioning strategy

## Alternatives Considered

1. **REST API calls**: Tight coupling, no audit trail
2. **Shared database**: Tight coupling, scaling issues
3. **Message queue**: Similar, but less flexible than event bus
